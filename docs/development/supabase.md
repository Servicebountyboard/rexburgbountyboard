# Supabase setup

The app uses the tables documented in [the schema reference](../architecture/database-schema-reference.md). The SQL migration adds security policies, indexes, and functions, and hardens the existing signup trigger function. It adds no table or column.

1. The project preflight was reviewed on 2026-10-13. It has no users or bounty data, no existing policies, uppercase status rows, and an Auth trigger that creates profiles. If running against a different project, first run [`preflight.sql`](../../supabase/scripts/preflight.sql) and review its results.
2. The migration [`20261013000000_connect_prototype.sql`](../../supabase/migrations/20261013000000_connect_prototype.sql) was applied to the project and [`postflight.sql`](../../supabase/scripts/postflight.sql) passed. For a different project, run the preflight and review its results before applying the migration. The migration adds security logic on existing tables and reuses the existing profile trigger.
3. Enable email/password sign-in and decide whether email confirmation is required in Supabase Authentication. The app supports confirmation links and requires confirmed email for posting, claiming, reviewing, messaging, and rating.
4. In Authentication > URL Configuration, add redirect URLs for the environments you actually use. For a native development build, add `mobile://auth/callback**`. For local web on port 8081, add `http://localhost:8081/auth/callback**`. For **Expo Go**, the Verify screen now displays the exact `exp://.../--/auth/callback?flow=verify` URL generated on your device. Add that exact URL to Redirect URLs, keep the Expo server running, then resend the confirmation email. Add the corresponding `?flow=reset` URL if testing password reset. Expo Go's URL can change when the server restarts; a development build provides a stable native redirect. Keep the allowlist as narrow as possible.
5. Copy `.env.example` to `.env` and set `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_KEY` to the project's URL and **publishable** key. Restart Expo after changes. These client variables are public by design; keep service-role keys and database credentials out of the app.
6. Start local web with `npx.cmd expo start --web --clear`. Create two accounts in separate browser profiles, or use separate devices. Confirm both emails. Post a bounty as one user, claim as the other, accept the claim, exchange a message, submit work, approve it, and verify the hunter receives points once.

Native email links using the PKCE flow need to open on the same device where signup or reset started. If a confirmation link lands on `localhost:3000`, first try signing in: Supabase may have confirmed the email before redirecting. If the email is still unconfirmed, add the Expo Go URL shown in the app and resend. Also check that the Supabase **Confirm signup** email template uses `{{ .ConfirmationURL }}` rather than a hardcoded `{{ .SiteURL }}` link. The app does not send device push notifications.

The built-in Supabase email service currently limits a project to two Auth emails per hour. If signup returns `email rate limit exceeded` during prototype testing, wait for the quota to reset. Alternatively, temporarily turn off **Confirm Email** under Authentication > Sign In / Providers > Email, create the test account, then turn it back on. Supabase implicitly confirms accounts created while that setting is off; do not leave it off if your release requires verified email ownership. A username used by an unconfirmed signup is still reserved by its profile, so choose a new username when retrying a signup made with the wrong email.
